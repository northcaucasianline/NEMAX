# Архитектура

## Поток сообщения

1. Клиент создаёт `clientMessageId` и отправляет сообщение в Core API.
2. Core проверяет сессию, права, ограничения и rate limit.
3. Сообщение получает глобальный `sequence`, шифруется и сохраняется.
4. Событие отправляется в Realtime. При недоступности Realtime оно остаётся в durable outbox Core.
5. Realtime доставляет событие по WebSocket или кладёт его в Redis offline queue.
6. Клиенты подтверждают события и восстанавливают состояние через `/api/sync?cursor=`.

Повторная отправка с тем же `clientMessageId` не создаёт дубликат.

## Core API

Core является единственным владельцем:

- состояния и транзакций;
- пользователей, сессий и прав;
- ключей серверного шифрования;
- объектного хранилища;
- проверки внутренних команд.

Realtime не читает базу напрямую.

## Realtime / Worker

Второй сервер отвечает за:

- WebSocket и heartbeat;
- online/offline presence;
- Redis offline queue;
- typing/recording;
- WebRTC offer/answer/ICE;
- повторную доставку;
- запуск фоновых задач Core;
- запрос смены серверного ключа каждые пять минут.

Взаимодействие защищено `INTERNAL_SERVICE_SECRET` и внутренними `/internal/*` маршрутами.

## Хранилища

- PostgreSQL — постоянное состояние;
- Redis — временные распределённые данные и очереди;
- S3/MinIO — зашифрованные объекты;
- локальные драйверы — fallback для разработки.

## Масштабирование

Core и Realtime можно разделять по контейнерам. Для крупного production следующий шаг — нормализованные таблицы сообщений/участников, PostgreSQL partitioning, NATS/Kafka для межсервисных событий, отдельные media workers и WebRTC SFU.


## Code Runner (`3003`)

Core API является единственной пользовательской точкой запуска кода: он проверяет сессию, право на проект и rate limit. В локальном режиме Core обращается к Runner по loopback TCP и `INTERNAL_SERVICE_SECRET`. В Docker Compose связь выполняется через Unix socket с файловыми правами; контейнер Runner не подключён к сети и не имеет доступа к PostgreSQL, Redis, MinIO или ключам сообщений.

Каждый запуск получает одноразовый временный каталог, ограничения времени, памяти, процессов, открытых файлов, размера создаваемых файлов и вывода. Родительский процесс в runner-контейнере подготавливает каталог, после чего пользовательский код запускается под отдельным непривилегированным UID/GID. Java компилируется в отдельный временный каталог, Python работает в изолированном режиме, а Node.js запускается с permission model.

Browser JavaScript preview отделён от backend runner: он выполняется в iframe без `allow-same-origin` и без сетевых запросов.


## Game Server (`3004`)

- хранит состояние игр отдельно от Core API;
- проверяет шахматные и шашечные ходы;
- управляет условными игровыми кошельками;
- запускает многостоловые турниры и кэш-столы Texas Hold’em;
- скрывает колоду и закрытые карты;
- отправляет обновления через Realtime;
- использует `GAME_DATABASE_URL` или `server/data/game-db.json`.

Подробности: [`GAME_SERVER_CHESS_CHECKERS_POKER.md`](./GAME_SERVER_CHESS_CHECKERS_POKER.md).

## AI Server

`server/ai-server.js` запускается отдельным процессом на порту `3005`. Core API остаётся единственным владельцем базы и расшифровывает только необходимый контекст конкретного ИИ-чата перед внутренним запросом. AI Server не подключён к PostgreSQL, Redis сообщений или хранилищу ключей. Его внутренние маршруты защищены `INTERNAL_SERVICE_SECRET`. Персонажи определены в `server/ai-personas.js`.
